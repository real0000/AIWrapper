# 驗證過什麼

CAGE 0.2.0 是評估版。這一頁明確說明每個部分測試到什麼程度，讓實地回報能送到真正有用的地方。

這裡用三個等級，而前兩個的差別，比聽起來重要：

| | 意思 |
|---|---|
| **能執行** | 在那一類的真實硬體上載入，並且產生了輸出 |
| **能載入** | 後端包在乾淨的環境裡能 `dlopen`、每個符號都解析得到、ABI 指紋相符，也能回報自己的身分 —— 但沒有那種 GPU，所以什麼都沒有計算過 |
| **未建置** | 沒有對應的套件 |

**「能載入」是真正的門檻，不是形式。** 它抓到過一些編譯零錯誤、卻載入失敗的後端包，因為從來沒有被實例化的 template，不會產生編譯錯誤，也不會產生符號。但它完全不能說明算出來的數字對不對。

除非某一列另外說明，下面的一切都是**拿 0.2.0 的套件本身**檢查的 —— 照安裝指南的說明解開到一個全新的資料夾，而不是拿開發中的建置。

## 後端包

在一台有一張 RTX 4070（compute capability 8.9）和八張 Tesla V100-SXM2（7.0）的機器上驗證；V100 分成兩個各四張的 NVLink 群組，群組之間只有經過 CPU 的 PCIe。

| 後端包 | 等級 | 細節 |
|---|---|---|
| `cuda-sm70_sm75` | **能執行** | 驅動全部八張 V100，並正確地拒絕 4070、說明原因。Qwen3-0.6B 在一張 V100 上大約 172 tok/s，在同一個 NVLink 群組的兩張 V100 上（`graph` 切分）、以及不同群組的兩張上（`layer` 切分）回答都一模一樣。照安裝指南安裝、由節點代理啟動的，以及 Docker 裡的 server，都在四張 V100 上回答了 |
| `cuda-sm80_sm86` | **能執行** | 驅動 4070（sm_86 的程式碼在 compute capability 8 之內向前相容） |
| `cuda-sm89_sm90` | **能執行** | 驅動 4070 |
| `cpu` | **能執行** | 自我測試通過 |
| `vulkan` | **能執行** | 驅動這裡全部九張卡 —— 4070 和八張 V100。AMD 的情況見下方 |
| `cuda-sm60_sm61` | **能載入** | **0.2.0 新增**，給 P40 和其他 Pascal 卡用。這裡沒有 Pascal 卡。sm_60 和 sm_61 各有 238 個 kernel，沒有 PTX；這台機器上的每一張卡都正確地拒絕了它 |
| `cuda-sm120_sm121` | **能載入** | 這裡沒有 Blackwell 硬體。這台機器上的每一張卡都正確地拒絕了它 |
| `hip-*`（全部五個） | **能載入** | 這裡沒有 AMD 硬體。在乾淨的 AlmaLinux 8、Ubuntu 20.04、Ubuntu 22.04、Debian 13 和 Fedora 容器裡檢查 —— 沒有 ROCm、沒有 AMD 驅動 —— 只裝了[安裝指南](server/server/backend-packs.zh-TW.md)為各個發行版列出的主機套件 |

**2026-11-25 重新建置。** server 和每一個後端包都以 ik `8c6a2b89f`、在 2026-10-31 開始使用的 Enterprise Linux 8 基底上重新建置 —— AlmaLinux 8、NVIDIA 的 Rocky Linux 8 CUDA 映像檔，以及 AMD 的 AlmaLinux 8 ROCm 映像檔 —— 用 GCC 14，以及相同的 CUDA 12.0、CUDA 12.9 和 ROCm 6.4.4。它們需要的不會比 glibc 2.28 更新：server 的執行檔最多要求 `GLIBC_2.28`，後端包和它們附帶的函式庫則是 `GLIBC_2.27`。每一個後端包都必須重建：server 跟後端包之間的介面改了，舊的後端包會被拒絕。每一個後端包都重新檢查過：能 dlopen、ABI 指紋跟 server 相符、回報 `8c6a2b89f`，並且在上面那台機器上，各自得到跟它那一列寫的完全相同的結果。`cuda-sm70_sm75` 那一列、下面安裝與 Docker 的兩列，以及更下面的測試套件，都用這些套件重新跑過。

**更舊與更新的發行版，沒有 CUDA toolkit。** 上面那台機器在系統層級裝了 CUDA，會掩蓋缺少的函式庫。所以 server 和全部十二個後端包，也在乾淨的 AlmaLinux 8（glibc 2.28）、Ubuntu 20.04（2.31）、Ubuntu 22.04（2.35）、Debian 13（2.41）和 Fedora（2.43）容器裡檢查過，沒有 CUDA、沒有 ROCm、沒有驅動，只裝了安裝指南列出的主機套件：server 能啟動，CPU 後端包的自我測試能跑，HIP 和 Vulkan 後端包能載入，CUDA 後端包需要的一切都能從它們自己的 `lib/` 解析到，只有 `libcuda.so.1` 例外，那是隨驅動提供的。這項檢查較早的一輪發現，後端包出貨時一直少了 `libcufft`；現在已經附上了。

**後端包並排安裝。** `cuda-sm60_sm61` 和 `cuda-sm70_sm75` 一起裝進同一個 `bin/`，就像一台 P40 插在 V100 旁邊的機器那樣。兩個都能載入；V100 的後端包接下八張 V100，Pascal 的後端包在這裡沒有東西可以驅動，兩者互不干擾。上面的 prompt 就是從這個裝了兩個後端包的安裝回答的。沒辦法檢查的是 Pascal 後端包實際驅動 P40 —— 這台機器上沒有。

**AMD，在另一台機器上。** 2026-09-28，gfx1150 後端包的 Windows 版照使用者會用的方式安裝，在 Radeon 890M 上跑過：0.6B 的聊天模型大約 91 tok/s、SD 1.5 圖片、語音、動作，以及完整的 TRELLIS 網格。Vulkan 後端包在同一張卡上跑聊天模型大約 23 tok/s，但在 SD 的第一步就當掉，語音輸出也是 NaN。那是較早一版程式碼的 Windows 建置；**這次發布的 Linux AMD 後端包沒有在 AMD 上跑過。**

## 安裝

| | 等級 | 細節 |
|---|---|---|
| 原生安裝，用 `install.ps1` | **能執行** | `dist/` 裡的 server 套件和兩個 CUDA 後端包，完全照[安裝指南](server-install.zh-TW.md)合併、安裝（`pwsh ./install.ps1 --prefix … --no-service`），再照 systemd unit 啟動它的方式 `cage-launcher --agent` 啟動：它啟動的 server 在 `bin/` 找到了後端包，並在四張 V100 上回答了 prompt；對節點代理送 SIGTERM 之後，一秒內全部結束。systemd unit 本身沒有安裝 |
| extension，從 `cage-0.2.0.vsix` 安裝 | **能執行** | 裝進全新的 VS Code 設定檔，連上上面那套原生安裝：settings.json 裡的權杖一啟動就搬進 VS Code 的 secret storage，server 上唯一的一張圖不用點就被選定並下載，本機模型在一張 V100 上回答，從 History 載入以前的對話之後，接著寫它的 session 紀錄 |
| Docker | **能執行** | [Docker](server/docker.zh-TW.md) 裡的快速開始，用 0.2.0 的 server 套件和 `cuda-sm70_sm75` 後端包：MySQL 和 server 都起得來、server 找得到後端包、照文件的方式登入（`Authorization: Basic`）可以用、模型在四張 V100 上回答、容器裡的 HTTPS 正常、帶著網頁 `Origin` 的請求被拒絕、網頁介面有回應，設定在 `down` 再 `up` 之後還在 |

在這幾輪測試之前，兩條路都跑不了本機模型。原生安裝時，安裝程式沒有複製 `lib/`，而由節點代理啟動的 server 會在安裝目錄找後端包，而不是在 `bin/`。Docker 則是映像檔建置不起來，產生出來的 `config.xml` 也解析不了。之前的測試都是在 `bin/` 裡面啟動 server，原生安裝的問題在那裡就不會出現。

這些是用打包好的 0.2.0 server 跑的，LLM 換成了腳本模型。它照腳本回答，所以檢查的是 server 這一邊：什麼送到了模型、寫了什麼、讀了什麼，以及順序。

|---|---|---|
| Session 紀錄 | 49 | 迴圈裡重跑的步驟會讀到上一次嘗試的報告；紀錄在執行回報完成之前濃縮；下一則訊息讀的是濃縮後的版本；新的 chat 是隔離的；沒有記憶 AI 的 config 時，紀錄會寫，但不會讀；接在 Memory 節點上的步驟自己掃，看得到自己上一次的報告 |

## 0.2.0 沒有建置的

| | 原因 |
|---|---|
| **Windows** | 能建置、能執行（見上面 AMD 的說明），但在另一台機器上；這次發布沒有產出 Windows 套件 |
| **aarch64**（DGX Spark、GH200） | 交叉編譯時，nvcc 的前端解析不了 aarch64 的系統標頭，而手邊沒有原生的 aarch64 機器。見[交叉編譯](https://github.com/real0000/AIWrapper/blob/main/server/cross/README.md) |
| **macOS** | Xcode SDK 的授權、Metal 編譯器和程式碼簽署，都需要一台 Mac |
| **`cage-rpc-worker`**（多節點） | 它是唯一還靜態連結 CUDA 的執行檔，所以綁定特定的 GPU 架構。它應該放進後端包；這一步還沒做，而且這條路本來就從來沒有驗證過 |

## 值得回報的

依能告訴我們多少排序：

1. **P40，或任何 Pascal 卡。** Pascal 後端包是新的，從來沒有驅動過任何一張。embedding 模型能不能載入，檢索回傳的結果合不合理？請附上 `bin/cage-backend-probe` 的輸出。
2. **Linux 上的任何 AMD 卡。** 模型能不能載入，答案對不對？Windows 版在一張 AMD 卡上跑過；Linux 的後端包從來沒有。
3. **Blackwell（RTX 50xx）。** 同樣的問題，同樣的原因。
4. **AMD 或 Intel 上的 Vulkan。** 這個後端包的存在，是為了讓非 NVIDIA 的硬體不用 ROCm 也能用。在它碰過的那一張 AMD 卡上，聊天能用，圖片和語音不行。
5. **任何 `cage-backend-probe` 跟實際情況不一致的情形** —— 它說某張卡能用、載入卻失敗，或反過來。server 信任的就是這個探測；如果它錯了，下游的一切都會跟著錯。

不加參數執行 `bin/cage-backend-probe`，會印出它找到的東西。那份輸出，是最值得附上的一樣東西。
