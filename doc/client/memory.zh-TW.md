# 專案記憶

CAGE 會替你的專案記筆記，並把相關的部分放進一輪執行裡。筆記分三種，各自由誰來寫的規則不一樣。

**檔案歷史**替你寫好：每個原始檔一份，記錄改了什麼、為什麼改。**session 紀錄**也替你寫好：目前這段對話的每一步做了什麼，讓迴圈裡再跑一次的步驟，看得到上一次嘗試發現了什麼。**規則**由你寫：長期有效的指示，適用時才載入 —— 你要求的話，AI 也會照你訂的條件往裡面加東西。

三種都放在專案的 `.cage/` 裡，是你能讀、能改、能 commit 的純 Markdown。一輪執行要讀其中哪些，由記憶 AI 決定 —— 見[讀哪些記憶](#讀哪些記憶)。模型的檔案工具打不開 `.cage/`，檢索也不會索引它，所以送到一個步驟手上的，就是記憶 AI 挑的那些。

---

## 自動寫下的檔案歷史

每一輪結束時，server 會為實際寫入過的每個檔案記一筆，寫進 `.cage/files/<path>.md`。之後的執行要等記憶 AI 挑中它才會讀 —— 見[讀哪些記憶](#讀哪些記憶)。

- **哪些檔案**，看的是 `write_file` 和 `apply_patch` 實際碰過什麼 —— 不是模型自己對這一輪的描述。模型常常聲稱建立了根本沒寫過的檔案，照它的說法記，就會替不存在的檔案捏造歷史。
- **為什麼**，取自節點的 Summary 輸出，壓成一行，讓這個檔案人讀起來也清楚。
- **沒有 Summary 的節點什麼都不寫。** 只回傳通過／失敗報告的建置驗證步驟，沒有什麼理由好記。

`remember` 工具讓模型可以刻意往同樣的檔案裡加東西 —— 適合記它*試過又放棄*的做法，這是任何 diff 都看不出來的。檔案歷史不依賴它：server 不管怎樣都會寫。

這是刻意的。以前 `remember` 是唯一的寫入者，而在三次測試執行裡，模型一次都沒有決定呼叫它。`.cage/files/` 從來沒被建立，每一輪載入的都是空的。

## 自動寫下的 session 紀錄

每段對話有自己的檔案 `.cage/sessions/<session id>.md`，由 server 在圖執行時寫入：

- **每個 Send To AI 步驟之後**記一筆：時間、節點的標題、它的 Summary 輸出原文 —— 沒有 Summary 的節點則是整份輸出 —— 加上那個步驟寫了哪些檔案。產生圖片、音訊或網格的步驟，會記下它產生的檔案。
- **每則訊息是一個段落**，標題是它的開始時間和訊息的第一行。執行結束時、在回答標成完成之前，記憶 AI 會把那個段落濃縮成一份簡短的清單，下一則訊息讀的就是濃縮後的版本。沒有記憶 AI 的 config，或濃縮失敗、被停下的話，段落就維持原文。中斷的執行不濃縮；接續它時會寫進同一個段落，等它結束時再濃縮。
- **它跟著對話走，不是跟著 server。** session id 屬於你編輯器裡的那段對話，server 重新啟動也不會變，所以紀錄也還在。開一個新的 chat 就開一個新檔案；舊的留著。

重點在迴圈。一張會把某個步驟送回去重試的圖 —— 例如一個 coder 加一個建置檢查 —— 以前每一次嘗試都從零開始：在一次測試裡，coder 跑了三次，每次都重新檢查同一個建置環境，雖然第一次嘗試自己的摘要早就寫了它查到什麼。那份摘要，現在就寫進 session 紀錄。

什麼都不刪減：比節點的記憶預算還長的紀錄，會在除錯窗格裡回報，而不是被截斷。每一次讀取、寫入和濃縮也都會在那裡回報，包括舊版 extension 沒辦法寫紀錄的情況。

`.cage/sessions/` 在你的專案資料夾裡，所以除非你 ignore 它，否則會進 git。

## 規則，以及什麼時候適用

`.cage/memory-map.json` 是一張**路由表**。每一列說明一個規則檔什麼時候該載入，以及 AI 什麼時候可以往裡面加東西（這一項可以不填）：

```json
{
  "version": 1,
  "rows": [
    { "when": "",                       "file": ".cage/memory.md",    "write": "" },
    { "when": "編輯 C++ 程式碼時",       "file": ".cage/types/cpp.md",
      "write": "我們決定新的 C++ 慣例，或踩到值得避開的陷阱時，記下規則和原因" },
    { "when": "跟 GPU 擺放或 VRAM 有關的任何事", "file": ".cage/gpu.md", "write": "" }
  ]
}
```

| 欄位 | 意思 |
|---|---|
| `when` | **自然語言**，不是 glob。空的表示永遠適用 |
| `file` | 規則檔相對於專案的路徑。不能用變數 —— 直接寫出檔名 |
| `write` | **自然語言**：AI 什麼時候該寫這個檔案、寫什麼。空的表示唯讀 |

空的 `when` 是確定的：檔案永遠會載入，不必呼叫模型。無條件的規則就放這裡。「一律用繁體中文回覆」不是需要判斷的事，每次都去問模型要不要遵守，是問錯了問題。

不是空的 `when`，在執行時由模型判斷。如果沒有設定記憶 AI 的 config，沒有東西能判斷，**這一列就當作適用** —— 漏掉你寫的東西，比多放一條規則更糟。

### 為什麼用自然語言

`when` 以前是 glob。使用者一直往裡面寫描述，`minimatch` 把它們編譯成什麼都比對不到的 pattern —— 那一列就默默地永遠不觸發，哪裡都沒有警告。大家想表達的，通常是「我在做這類工作的時候」，而不是「路徑長這樣的時候」。

舊的 glob 寫法仍然會讀，編輯器會提醒你改寫。`*` 和 `**` 會直接轉換、不另外提醒，因為它們本來的意思就是「永遠」。

### 怎麼編輯

**Chat → 🧠 Memory** 可以編輯這張表 —— 一列三個欄位：`when`、`file`、`write`。存檔會寫入 `.cage/memory-map.json`；監看程式會把它推給 server，server 再把解析警告送回來。

它放在 Settings 旁邊、而不是 Logic Editor 裡，因為它屬於**專案**，不屬於某一張圖：這個專案的每一張圖，讀的都是同一張表。圖自己決定的是由哪個模型做判斷 —— 也就是 Logic Editor 的 Memory 區塊裡的 Memory AI Config。

server 不得不略過的列會被回報，而不是悄悄丟掉 —— 一列消失，會連帶帶走一整類記憶。

你也可以直接手動編輯 JSON。檔案不存在時會套用內建的預設值，所以你什麼都還沒設定，記憶就已經能用。

## 讓 AI 往規則檔裡加東西

`write` 就是全部的規格，用你自己的話寫 —— 觸發條件和內容都在裡面，因為你說出口時就是這樣說的：*「我們決定新的 C++ 慣例時，記下規則和原因」*。留空的話檔案是唯讀的，什麼都不會寫進去。這是預設值，所以既有的路由表行為完全不變。

你標成可寫的檔案，有兩條路會寫到它，兩條互相補位：

- **模型可以在這一輪裡寫。** 可寫的檔案會列在它收到的記憶區塊裡，`remember` 接受一個 `target`，指定其中一個。其他的一律拒絕 —— 路由表是唯一的關卡，而且是在 client 檢查，因為表就放在 client 那邊。
- **Send To AI 節點結束時，server 會檢查。** 它問記憶模型：剛剛發生的事符不符合你的指示，符合的話要記哪一行 —— 一次呼叫涵蓋所有可寫的檔案，而且只在節點真的產出了東西時才做。會有這一條，是因為光靠模型自願不夠：`remember` 是唯一寫入者的時候，三次測試執行下來，它一次都沒被呼叫過。（在有好幾個 Send To AI 節點的圖裡，每個跑到的節點都會做這個檢查，所以記憶模型要選小的。）

不管走哪一條，那一行都會加上時間戳記，**附加**在規則檔的最後面，在你自己寫的內容下方。（檔案歷史則相反，最新的在最上面，因為那個檔案是當成 log 讀的。）兩條路不會重複寫：這一輪模型已經寫過的檔案，輪末的檢查會略過。

一列的 `when` 同時管住這兩條路。只在「編輯 C++ 程式碼時」載入的檔案，在跟 C++ 無關的一輪裡不會被寫入。

**沒有記憶 AI 的 config，就不會自動寫入任何東西。** 這跟讀取那一邊刻意相反：漏載一條規則，代價是少一條指示；寫入沒經過任何判斷的內容，則是把沒人審過的文字放進你那個會進 git 的檔案。模型仍然可以自己用 `remember` 寫，因為那是它自己刻意做的事。

每一個決定都會在除錯窗格裡回報 —— 哪些檔案被列為可寫、寫了什麼，什麼都沒寫的時候又是為什麼。你填好的一列卻默默什麼都不做，正是這個功能必須避免的失敗。

## 讀哪些記憶

一個步驟執行之前，記憶 AI 會一次拿到所有候選 —— 路由表的每一列、專案裡的每一份檔案歷史，以及這段對話的 session 紀錄 —— 連同這個步驟接下來要做的工作，從中挑出跟它有關的。只讀挑出來的那些。

- **`when` 是空的列永遠會讀**，不管模型有沒有挑它。
- **`when` 判斷不出來的列，算作適用** —— 漏掉你寫的規則，比多一條更糟。
- **檔案歷史和 session 紀錄只有被挑中才會讀。** 訊息有沒有提到某個檔案，跟要不要讀它的歷史無關；看的是這個步驟在做什麼。
- **沒有記憶 AI 的 config，就不讀任何檔案歷史和 session 紀錄。** 紀錄還是照寫；規則列照上面說的方式讀。

除錯窗格會列出每一樣沒讀的東西和原因：這次的工作沒挑它、沒有記憶 AI 的 config，或記憶 AI 挑選失敗。

**這在 0.2.0 改了。** 以前，檔案在場時才會讀它的歷史 —— 訊息裡提到、附加了，或被檢索找到。沒有提到任何檔案的步驟 —— 迴圈裡大多數的步驟都是這樣 —— 完全不讀歷史。

## 記憶 AI 的 config

挑選要讀什麼、濃縮 session 紀錄、決定要寫回什麼，都是模型呼叫，由圖層級的 **Memory AI Config** 設定。節點會繼承它，也可以覆寫。不設的話，每一條有條件的列都當作適用，不讀任何檔案歷史或 session 紀錄，session 紀錄維持原文，也不會自動寫入任何規則檔。

小而快的模型才是對的選擇 —— 判斷很短，而且是在真正的工作之前跑。
