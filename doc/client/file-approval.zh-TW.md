# 檔案核准

`write_file` 和 `apply_patch` 會直接寫進你的工作區 —— 但要先等你核准它們即將碰到的那個檔案。一個檔案，一個問題，在寫入的那一刻問。

沒有暫存區，最後也沒有批次審查。工具回傳時，檔案要嘛已經在磁碟上，要嘛被拒絕了，而模型會被告知。

---

## 你會看到什麼

每一筆等待中的寫入，都會在 chat panel 裡以自己的卡片出現：

| | |
|---|---|
| 路徑 | 相對於工作區的根目錄 |
| 種類 | 寫入、patch 或刪除 |
| 大小 | 寫入之後檔案有幾個位元組 |
| Diff | 跟磁碟上現在的內容比較的 unified diff，有語法上色。刪除或二進位檔案時是空的 |

核准的話，工具會寫入，然後回報檔案已經在磁碟上。拒絕的話，什麼都不寫；模型會被明白告知它被拒絕了，然後繼續。

## 一次一個問題

核准會**依序排隊**。任何時候都只有一個請求在等你；其餘的照抵達順序排隊，這段期間進來的工具呼叫也會先擱著，等你回答完眼前這一個。

這比聽起來重要。一個碰到五個檔案的 `apply_patch` 會問五次，每次附上那個檔案自己的 diff —— 不排隊的話，你會同時看到五張卡片，分不出哪張是哪個。模型也會在幾毫秒之內送出兩個工具呼叫，它們會排隊，而不是互相搶先。

檔案核准和[工具核准](tools.zh-TW.md)共用這一個佇列，所以 `run_terminal` 的請求不能插隊到你還在考慮的寫入前面。

## 檔案寫到哪裡

相對路徑會落在你的工作區根目錄。檔案寫到哪裡不是 server 決定的 —— 路徑來自 client，而且每一條路徑在詢問你之前，就已經跟 **Settings → File access** 比對過了。

## 專案以外的檔案

檔案工具只在工作區資料夾，以及你在 **Settings → File access**（`cage.fileAccess.*`，見[設定](settings.zh-TW.md#file-access)）裡允許的路徑裡活動。symlink 以它實際指向的地方為準：專案裡一個通往別處的連結就算是別處，壞掉的連結也是 —— 透過它寫入，會在它指向的地方建立檔案。

其他任何地方，在 **Anywhere else** 設成 *Ask each time*（預設值）時，卡片是紅色的，寫出真正的位置，而且只有 **Allow once** 和 **Deny** 兩個選擇：

- 在那裡讀取或打開檔案也會問，不只是寫入。
- **Allow all (Session)** 和自動允許的寫入都不涵蓋它。專案以外的每個檔案，每一次都會問。
- 要讓某個地方不再被問，把它加進允許的路徑。

設成 *Refuse without asking* 時，工具會拒絕，模型會被告知你的設定不允許。碰到任何一個專案以外檔案的 `apply_patch`，會整份被拒絕 —— 裡面的檔案一個都不寫。

`run_terminal` 和 `run_code` 不在這個範圍內：它們執行的是指令，你的帳號碰得到的東西它們都碰得到。它們有自己的核准 —— 見 [Tools](tools.zh-TW.md)。

## 為什麼這樣設計

早期的設計是把寫入累積在每個 session 的暫存區裡，再請你一次批次寫出。實際使用時，它有三種失敗：

- 模型被告知它的檔案*已暫存、還沒寫到磁碟*，於是一再重寫同一個檔案，想讓它生效 —— 有時甚至改用 shell 的 heredoc，完全繞過這個工具。
- 一輪裡從來沒執行過終端機指令的話，每一筆寫入都懸在那裡。執行結束了，卻什麼都沒發生。
- 真的跳出詢問時，是要你一次審查一大堆互不相干的檔案。

立即、逐檔的核准要多點幾下，但這三種失敗全部消失。模型對工作區的認知，現在就是事實。

## 實際使用

- **調整 `run_terminal` 的核准，不會影響這裡。** 檔案核准不是一種工具核准模式；沒有任何設定能讓寫入變成自動。
- **拒絕的代價很小。** 模型會被告知，可以提出別的做法。這不是錯誤，也不會結束這次執行。
- **真正碰得到外面的，仍然是 `run_terminal`。** 它在你的機器上執行真正的指令，能碰到任何檔案關卡都看不到的路徑。這就是它預設為 `ask` 的原因。
